# GEP/1 synthetic implementation protocol

The server accepts bounded JSON (256 KiB, 64 events per batch, 10,000 events per session, depth 16). The admin export application route has its own bounded 1 MiB envelope described below; every other route keeps these participant protocol bounds. JSON duplicate keys, nonfinite values, negative zero and numbers outside the JavaScript safe integer magnitude are rejected. Object order is irrelevant; arrays preserve order; booleans differ from numbers; null differs from absence. JSON Schema 2020-12 payload definitions are frozen with builds. No remote references are permitted by the build registration contract.

Records have immutable UUID event/session/segment identities and positive segment sequence numbers. Retries preserve all record fields. A batch commits atomically or fails completely. ACK accepted/duplicate lists must exactly cover the request. An HTTP status alone is never an ACK.

## Client delivery accounting (03 remediation engineering)

The Web SDK and the native backend persist a versioned per-session delivery record (`delivery_version: 2` plus `initial_failed`, `retry_failures`, `round_id`, `last_error`, `last_error_kind`, `ack_progress`, `terminal_reason` and `inflight`) in the same durable transaction as the queue itself. Reading an older queue only fills the missing defaults: the legacy `attempts`/`retry_at`/`paused` budget, the records, the proof and the admission binding are never reset or rewritten. The legacy 32-attempt safety budget stays independent of the three-failure display threshold.

Only a validated ACK whose local transaction really reduced `pending` (or durably saved a valid completion ACK) counts as progress: that queue change and the progress (`ack_progress` increment, consecutive retry counter reset) commit in one durable transaction, so an interrupted round can never leave a queue without its count. An HTTP 200 without the exact accepted/duplicate coverage, an invalid completion ACK (every list — accepted, duplicate, missing, declaration event and segment ids — must be a real, correctly typed array that exactly matches the fixed binding and set, including for an empty completion set) and a local write failure are no progress. The first normal send failure after the declared completion only sets `initial_failed`; each subsequently executed retry round that ends without persisted progress and with a retryable failure increments `retry_failures`. A round persists `inflight` and a new `round_id` before any request, sends at most one event batch (at most 32 events) and, only when no `pending` record remains, the completion request; a process exit in the middle of a round is recorded as `outcome_unknown` and is never counted as a failure. The durable retry schedule (backoff or `Retry-After`) is respected by automatic and manual rounds alike; neither clears the counters or lifts a safe pause. A server refusal marked `retryable:false` (any status, not only 401/403/409/422) is a safe pause without counting, while a local storage failure is reported separately as a local error, produces no progress and stays retryable instead of being treated as a remote authorization denial. A permanent `study_deleted` refusal terminates immediately whether it arrives during the experiment, on a completion-only round or after a legal batch ACK in the same round; it stops further sending and keeps the legal, unlocked local export available.

Completion declares explicit event and segment UUID sets. It can precede uploads and stays pending until the declared events arrive. Once declared, additional events outside the set are rejected. Completion is a data collection fact, not scientific acceptance or backup confirmation.

Admission uses an operation UUID plus a private client-generated proof, persisted before the first request. Repeating the same operation requires its proof and binding; a public operation UUID cannot retrieve the session credential. Participant codes are scoped to a study and preserved as strings. Session bearer credentials never authorize administration or RAW reads.

These limits and protocol tests are synthetic engineering evidence. Browser/native persistence and end-to-end acceptance remain separate gates.

Recovery requires a study-authorized, unexpired one-time permit plus the original private recovery proof. Public participant/session identifiers are insufficient. Successful reauthentication atomically persists renewed credentials and resets the paused upload retry budget; a rejected permit cannot unpause it. The response includes `task_finished`. A local or server completion declaration forces data-only recovery: no new trial, segment or completion-set expansion. Experiments without a declared compatible recovery strategy also recover data only.

## Versioned same-device recovery (03D engineering)

The long-permit recovery above is unchanged. A separate route `POST /v1/participant/recovery` accepts exactly one versioned capability and fails closed with `unsupported_capability` (409) for anything else.

`recovery_code/v1` carries a six-digit code a study-authorized researcher issued for one session, plus the device's original private proof and the frozen `instance_id`/`study_id`/`release_id`/`build_id` binding. No public session or participant UUID is required, because the server resolves the session internally. Issuance requires current `session.recover` (with its `study.view` prerequisite) on a live account; the code lives five minutes, is bound to one session/study/release/issuer, allows at most five failed attempts, and a newer issuance invalidates the previous code. Only a server-secret HMAC of the digits is stored. The code alone discloses nothing: a wrong code, proof or binding returns the same `recovery_denied` (403) without a session credential, and a consumed code cannot be replayed. Issuance and redemption are rate-limited by bounded study, client and instance keys, never by the code or proof itself, so one client's failures do not lock other clients. A revoked session stays unrecoverable, and a successful redemption renews the session without touching its completion declaration.

`recovery_named/v1` is the explicit same-device continuation for a frozen password-mode release: it requires the original private proof, the matching roster participant code and the configured password, the same binding and an active, unexpired roster entry. A public participant code alone restores nothing, and a device that reports `front_locked` is refused (`front_locked`, 403) and must use the issued code or long permit path instead.

Both capabilities answer with the renewed session credential, `session_id` and `task_finished` only; a finished queue recovers data only under its original closed completion, never trial replay. Issuance and redemption write secret-free audit rows. The GEC participation shell now renders these inputs directly: a secondary six-digit panel and a named same-device continuation. A candidate returned by either capability is never resumed automatically - the shell asks for an explicit continue (or, for the named path, an explicit new session) and the device proof, the persisted foreground lock and the matching local candidate are checked first. The long-permit path stays available as an advanced compatibility panel. This is synthetic engineering evidence.

New participation locks older active sessions out of foreground recovery; it does not erase their unacknowledged data or modify already cleaned tombstones. Cleanup requires the complete declared event set, a durably saved valid completion ACK and no pending records or recovery dependencies. Transaction/process interruption is covered separately for IndexedDB and native SQLite; physical power-loss and secure-erasure guarantees are outside this acceptance.

## Study entry, public listing and the current release

The additional fields below were added in the Phase 03 03C delivery and are covered by synthetic engineering tests, not by human acceptance.

A study is listed publicly only when the researcher explicitly marks it public, recruitment is open and the study has a current release that is approved and resource-located. Private and roster studies never become public through recruitment or authentication mode, and a study without a current release does not open new participation through the portal. A closed study is only shown as an opted-in summary without any start.

The stable study entry on the experiment origin reports the current release and publication revision it observed. A new participation request can bind them instead of a direct release:

- Stable-entry admission uses `study_id`, `expected_release_id` and `expected_revision` instead of `release_id`.
- The start click carries that observation through the platform entry gate: the release application is only served while the binding is still the study's current, open, approved and resource-located release, and the validated `expected_release_id`/`expected_revision` are injected into the application context so the shipped client sends them with its create request. A page whose binding is superseded receives the entry-refresh page (409) instead of the application and creates no session.
- A create request that carries the stable-entry binding is validated as a stable entry even when it also carries `release_id`; only a request with `release_id` alone uses the frozen direct-release contract.
- If the current release or the publication revision changed after the page loaded, the request is refused with `stale_entry` (409) and no session is created; the server never silently switches materials.
- Repeating an existing create operation with its original proof and binding returns the original session even after the current release changed, before any new current-release policy is applied.
- Direct `release_id` requests keep their frozen original admission contract (approved release plus open recruitment) and are never redirected to another release. Existing sessions, uploads, recovery permits, configuration downloads, exports and resource URLs stay bound to their original release and are not rewritten.

## Public participation links

The personal site only links to the participation portal; the portal and experiment resources are served on the experiment origin, and the researcher workbench stays on its own origin with a host-only management cookie. `GEP_ADMIN_HOST` (default `admin.localhost`) configures that workbench origin, and every admin route, including raw-data export creation and download, accepts exactly the configured origin plus the explicit local `localhost`/`testserver` links instead of every entry of `ALLOWED_HOSTS`, so changing the configured origin also closes the previous one. Real domain, DNS and TLS deployment remain future work and are not part of this implementation.

## Study deletion and the permanent refusal table (R04 engineering)

A v2 study can be permanently deleted by an actor holding `study.delete`, after re-entering their own password; the mark (job row, session tombstones, `lifecycle='deleting'` and the audit) commits in one transaction that shares its boundary with admission, event upload, completion, recovery issuance/redemption, publication and export creation. A transaction that commits before the mark is included in the cleanup; a request that arrives after the mark never writes. The database rows are removed later by the explicit, bounded, re-entrant `cleanup_deleted_studies` maintenance command (no resident daemon), and the state only becomes `complete` after the database rows and the private files are verified gone.

Deletion tombstones (`DeletedSession`) keep only the session/study/release/build/instance UUIDs and server-secret, domain-separated HMACs of the already-hashed token and proof, plus a dedicated operation-binding HMAC that ties the original operation to its instance/study/release binding. The submitted token/proof is digested and HMACed the same way before a constant-time comparison; the operation HMAC is recomputed from the submitted operation and the binding the interface can resolve, and a build is additionally compared whenever one is provided. A match can only refuse; it never restores a read, a write or a re-issued credential, and no raw token, proof, roster, answer or password is stored.

The refusal table below is fixed; no route uses a bare `410`, because existing Web/native clients treat 401/403/409/422 as a safe pause:

| Request | Matching deletion tombstone | Unknown / forged / random |
| --- | --- | --- |
| New admission or old operation retry (`POST /v1/participant/sessions`) | 403 `study_deleted` (only the original operation, its exact instance/study/release/build binding and the original proof) | 403 `admission_unavailable` |
| `event-batches`, `completion`, `context`, `status` | 403 `study_deleted` (matching token) | 403 `session_unavailable` |
| Old `/v1/participant/sessions/<id>/recover` and `POST /v1/participant/recovery` | 403 `study_deleted` (original proof plus exact binding) | 403 `recovery_unavailable` |
| Public `join`/`run`/download/preview | 404 (same as a random id) | 404 |
| Admin export download, release config/artifact, build preview | 404 `export_unavailable` / `not_found` (same as a random id, even for a former authority) | 404 |

A fresh operation that merely reuses the original proof is not the original operation and stays `admission_unavailable`; a retry after the cleanup removed the release row still carries its own request binding and can still receive `study_deleted`. Study-scoped management writes (publication policy, current release, roster and permission preview/commit, account imports that name the study) re-check the lifecycle inside their final locking transaction, so a request that read the study before the mark committed is still refused and no new permission, roster or private preview is created for a deleted study. All refusals carry `retryable: false` and `outcome_unknown: false`, and none reveals a study name, roster, state or count. The deletion requester or the instance Owner may still see the minimal job progress (state, requested time, real counts recorded at the mark, persisted error code) and never the study title; everyone else sees the same 404 as an unknown object. Retained audit actions stay attributable to their study: the study foreign key is nulled and a minimal `Audit.study_uuid` remains (rows already detached before that field existed stay unknown), while raw `before`/`after` values of the deleted study are cleared and the mark row keeps its minimal counts. Database rows are removed in bounded, re-entrant batches, and file cleanup is bounded by real removals: each batch removes at most `--batch-size` files, counting an export ZIP and every interrupted `.<uuid>.<16 hex>.tmp` file or link as one unit; an export spool that is not completely removed stays in the persisted manifest, a file-only run continues while it really removes files, and `complete` is only written after the database rows and the private files are verified gone. Illegal `--batch-size`/`--max-batches` values exit non-zero before any cleanup. Old frozen client packages are never rewritten.

## Frozen raw-data exports (v1 preserved, v2 engineering)

Raw-data export creation and download stay on the configured admin origin. `POST /v1/admin/exports` without `format_version` keeps the frozen v1 contract byte for byte: records with their `builds`/`sessions` sidecars, no roster and no title; an explicit `format_version` must be exactly the string `"1"` or `"2"`, and anything else fails closed (`export_format_version`, 400). Downloads never back-fill a v1 snapshot from the current database, so a late event, a rename or a changed roster leaves the original bytes untouched.

A v2 application names `view` (`identified`/`unmapped`) and `language` (`zh`/`en`) explicitly and may carry an explicit `session_ids` range of up to 20,000 session UUIDs; unknown, cross-study, duplicate or malformed ids are refused (`export_scope`, `export_scope_unknown`) instead of being omitted, and older `GET`/`POST` callers keep the v1 response shape. The export application route has its own request envelope of 1,048,576 bytes and an array bound of exactly 20,000 entries, so one complete range is really delivered over authenticated HTTP; a range over the ceiling is refused (`array_limit` at the envelope, `export_limit_sessions` in the export core) instead of being silently narrowed, and every other route keeps the unchanged participant bounds above. Creation freezes one consistent transaction's view of the study title, the roster, the sessions, the events and the involved build descriptors inside the export row. `identified` freezes `data.export_raw` plus `identity_mapping.read` and keeps the participant code (a null code stays null in the frozen JSON and renders as an empty cell); `unmapped` freezes `data.export_raw` only, never stores a code and lists only participants that really have a session in range. Every format re-checks the frozen requirement set on creation and on every download, so a revoked grant refuses the whole export instead of degrading it. Frozen `created_at`/`received_at` values are ISO 8601 UTC `Z` with source microsecond precision, and sessions keep their real creation order (created_at, then UUID). Version-2 metadata is the fixed whitelist `id`, `format_version`, `view`, `language`, `study_id`, `title`, `created_at`, `counts`, `limits`, `field_contract`, `csv_encoding`; the frozen selection is nested in `limits.scope` as `{"mode": "study"|"sessions", "session_ids": [...]}` and is read from the frozen snapshot, never recomputed from the current database, so a full study, a selected range and an empty range stay distinguishable. The stored snapshot is never passed through. The v2 JSONL download is the lossless path and is never subject to a spreadsheet cell limit; a single-file v2 CSV is refused (`export_zip_required`, 409) because the v2 CSV pair belongs to the ZIP bundle. `GET /v1/admin/exports/<id>/download?format=zip` delivers exactly two members, `participants.csv` and `events.csv`, in that order, with the frozen columns, headers, BOM and RFC 4180 quoting; the download file name is the immutable export UUID (`<id>.zip`), never the study title or another request value. The ZIP is assembled from the frozen snapshot, written to a private temp file, flushed and fsynced, and only then published with one atomic rename; a leftover temp file is never served. Because the package bytes are a deterministic function of the frozen snapshot, a stored file is served only after the same opened file has been compared byte for byte with the fresh rebuild of this export: a valid ZIP of another view, language or export is replaced instead of served, a missing, truncated, wrong-member or symlinked file counts as an unknown state that is never followed or served, and a symlinked spool component is refused before anything outside the spool is written. The served bytes are always the bytes that were verified in that request; no unchecked path is re-opened after validation. The final compressed ZIP and the decompressed CSV pair are both bounded to 64 MiB (published in `limits` as `max_zip_bytes`), and the generation deadline covers serialization, compression, cache comparison and the file commit, so an over-budget run leaves no READY file. A disk failure at any point refuses the download (`export_generation_failed`, 503, `jsonl_available: true`) without a `Content-Disposition` header and without a half package; a package over the ZIP boundary is refused (`export_limit_zip`, 413, `jsonl_available: true`) and the lossless JSONL path stays available. Concurrent same-export requests share one atomic publication: a cleanup only removes the exact file that request published (device and inode identity), so it can never delete a successful download or serve mixed bytes. Creation enforces event, participant, session and snapshot UTF-8 limits; CSV rendering separately enforces pair-size and cell limits, and an over-limit cell refuses only the ZIP while the JSONL path keeps the whole payload. Version-1 exports have no ZIP: an explicit `format=zip` request on a v1 row fails closed (`export_format`, 400) and every v1 format stays byte-frozen. `tools/remediation_export_capacity.py --verify` measures the maximum-size synthetic sample and each exact boundary independently of the request path.

## Complete native distribution artifact (03D engineering)

A native program is registered from its descriptor and then uploaded as a bounded archive of exactly one `.app` bundle (256 MiB packed, 512 MiB expanded, 4096 files, compression ratio 200). Traversal, absolute, colliding, linked, script and non-regular members are rejected; the bundle must ship its executable, `Info.plist` and PCK resources, and the archive digest must equal the registered program digest, which deliberately excludes the external connection configuration.

Approving such a release preallocates the release id, freezes the public configuration (mode and `shell_capability` included), copies the program bytes and executable modes unchanged, materializes the frozen schema and codebook, adds the project license and the bundled third-party notices, and writes `artifact_manifest.json`. That manifest lists every member with its SHA-256, size and mode, names the program digest and the configuration digest, and never contains the digest of the complete package; the outer SHA-256 of the finished file is stored only in the release row. Assembly is validated before one atomic rename, a released artifact is never overwritten, and an interrupted or failed assembly leaves the previous release reachable.

The complete package always carries both `LICENSE` (the project license) and `THIRD_PARTY_NOTICES.txt`: the latter reproduces, unchanged, the official Godot engine license and its bundled third-party copyright/license documents (the engine's own `Engine.get_license_text` / `get_copyright_info` / `get_license_info` output) plus the vendored godot-sqlite license and the SQLite public-domain statement. The project license alone is never presented as the license of the bundled engine or addon; the frozen engine document is compared against a fresh export of the official local engine during engineering verification.

`GET /releases/<release_id>/artifact` and `GET /releases/<release_id>/artifact/<member>` serve the complete package and its sidecar members (manifest, `connection.json`, schema, codebook, license, third-party notices) only to an account that still holds the build scope on that study; the program bundle itself is only served as the whole package. Every response re-verifies the stored bytes against the recorded digest, so tampered or missing artifacts are refused instead of distributed. A release frozen with a complete artifact is admitted only while that artifact is present and byte-intact: a failed check returns `release_unavailable` (409) before any session is created. Descriptor-only registrations and Web packages keep their original contracts, and an artifact manifest with an unknown format version fails closed.

The current release is platform-aware. A Web release offers the browser start on the portal and stable entry only while it really carries a stored Web package; a complete native release is presented as a controlled independent program with its own participation explanation and never gets a fabricated `/run/<release_id>/web/index.html` path, because a program archive contains no Web application. The controlled package download stays behind the build scope and is never turned into a public portal download; a native release whose stored artifact is missing or tampered is presented as unavailable (and omitted from the public list) instead of offering a start. Descriptor-only native registrations are never presentable and never selectable as the current release, while their legacy registration, approval, connection-config export and direct admission contracts are unchanged.

The downloaded macOS package contains `connection.json` next to the `.app`, so the exported program launches with its bundled default configuration and needs no manual file replacement. The synthetic engineering evidence for this contract is recorded in the verification log.
