# Windows x64 原生完整包：自导实机体验指南（中文）

本指南供**原设计者自主体验验收**使用。目标是在真实 Windows x64 电脑上按自己的节奏走完 WN01–WN06，
不需要开发者逐步讲解。全程**不需要输入任何命令**：需要执行的检测由准备者与测试工具完成，
你只负责在界面上真实操作、观察并记录（界面操作）。

工程检查与人类体验是两条独立门槛：本指南描述**界面操作与观察**；机器可读的工程结论由
`tools/windows_native_harness.py` 与 `tools/phase03_verify_windows_native.py` 产生，
放在本地忽略目录，不进 Git、不进入参与者包。本体验不等于独立 T17。

## 一、体验前：准备者已完成什么

1. **真实构建与真实发行**：Windows x64 程序由固定本机 Godot 4.7.2 与官方固定模板交叉导出。
   kit 内的每个完整包都是**从平台授权下载端点真实下载的字节**，由平台自己的冻结流程生成
   （公开配置 + schema + codebook + 许可证 + 第三方声明 + 成员清单），准备者没有重新打包、
   没有替换成员、没有改写清单。
2. **三个冻结研究**：三种参与模式各自是一个独立合成研究/发行（无需 ID、预发名单 ID、ID+密码），
   三者共用同一个不可变 Windows 程序构建。研究模式在批准发行时冻结，批准后**不能**再改；
   要换模式只能新建研究。
3. **独立合成实例**：独立数据目录、独立数据库、独立密钥与回环端口，不连接既有验收实例或真实数据。
   每个模式一个完整包，包内 `connection.json` 已冻结为本次实例的公开配置，位于 EXE 同级。
4. **真实账号**：名单账号经真实名单导入创建，受限成员经真实邀请流程创建并登录；
   可用账号在私有产物 `runtime_accounts.json` 中（不在参与者包内，也不随包分发）。
5. **运行前置条件**：冻结配置指向准备主机的回环端口，Windows 侧需要准备者提供的作用域 SSH 隧道
   （`operator/tunnel.cmd`）或等价的已验证 LAN 端点。没有这条隧道时程序无法准入，
   应记为“受阻”，不要修改防火墙、DNS 或证书信任。
6. **准备好的启动器**（双击即可，无需输入命令）：
   - `operator/designer-mode-anonymous.cmd`、`designer-mode-id.cmd`、`designer-mode-password.cmd`：
     解压对应模式的真实完整包到含中文与空格的目录，并用该模式独立的本地数据目录启动真实程序；
   - `operator/run-windows-checks.cmd`：运行工程检查（W N01–WN06 的可自动化部分）并写出机器可读报告。

## 二、实机操作步骤（无需输入命令）

### WN01 解压、直接启动与首屏

1. 用 `designer-mode-anonymous.cmd` 启动（它会解压到含中文与空格的路径，例如
   `桌面\GEP 原生测试 中文 anonymous …\`；不要放在 OneDrive 同步目录内）。
2. 观察首屏：应出现**参与界面**（不是编辑器、不是网页、不是命令行窗口）。
3. 如果 Windows SmartScreen 或杀毒软件出现提示，请在记录表里写清提示原文/弹窗类型
   （提示/拦截/无提示），**不要**关闭防护、不要添加信任、不要解除“仍要运行”以外的系统设置；
   遇到拦截即记录为现场失败并保留截图。
4. 记录：Windows 版本与内部版本号、是否需安装 Godot 或手工改配置（应为“否”）、
   解压路径是否含中文与空格、首屏是否可见、SmartScreen 观察结果。

### WN02 三种参与模式（三个冻结研究，同一构建）

依次用三个启动器各走一次（每次只影响该模式的新会话）：

1. **无需 ID**：直接进入任务界面，后台应生成新的会话 ID。
2. **预发名单 ID**：输入私有账号卡中该模式的 ID（例如 `001`），确认前导零保留且能进入。
3. **ID+密码**：先故意输错一次密码，应被**就地拒绝**并给出可理解提示（不跳原始 JSON）；
   再用正确密码进入。
4. 每个模式完成**两个试次**（本任务就是两个试次：按左/右键各一次，程序到达结束界面即声明完成），
   关闭程序，再回后台核对会话状态与实际一致。
5. 记录每个模式的界面提示、后台会话结果与所用账号 ID。

### WN03 本地保存、断网继续、重连补传、关闭重开、进程终止

1. 正常进入任务并完成第一个试次（本地应立即保存）。
2. **断网继续**：临时断开本机网络（例如关闭 Wi-Fi；不要修改系统防护/防火墙设置），
   继续完成第二个试次——界面应允许继续，并显示待上传状态，而不是假成功。
3. **重连补传**：恢复网络，等待自动补传完成；后台事件应补齐，重复不会变成两条。
4. **关闭重开**：关闭程序后重新启动，已确认与待传状态应保留，不应重做已完成试次。
5. **进程终止**：用任务管理器结束进程后重新启动；待传队列应仍在，恢复后继续上传。
   注意：本项只证明进程终止，不声称物理断电已验。
6. 丢 ACK 的重复提交由工程检查用受控故障注入执行（`run-windows-checks.cmd`），
   人工不需要构造；记录你观察到的界面状态即可。

### WN04 检查点恢复、短码、完成待传、共享设备锁

1. 在试次边界（第一个试次之后）关闭并重开，确认只恢复到事务完整边界，已完成试次不重放。
2. 需要恢复时，在后台为本次会话签发**六位短码**，在程序内输入短码并使用**原设备私密证明**
   （本机原程序自动持有，不需要你复制粘贴口令）。
3. 故意输入错误码、使用过期码、重复使用已成功消费的码：都应被拒绝并保留可理解提示。
4. 任务完成由**任务本身声明**（两个试次结束即声明完成），不需要研究者手动把后台标记成完成；
   已声明结束的会话再次恢复只补传数据，不会重做任务，已清理的本地墓碑状态应准确。
5. 共享设备场景：在已被另一个未结束会话占用的设备上发起新参与，不应误用旧的恢复绑定。
6. 记录每次拒绝的提示与后台审计/会话状态。

### WN05 失败数据导出与三方对账

1. 在仍有未确认上传数据时，使用界面提供的失败数据导出入口保存导出文件。
2. 打开导出检查：不应包含令牌、恢复证明、口令或完整凭据；导出**不应删除**本地队列。
3. 对账：本地 SQLite（程序数据目录中的 `queue.sqlite`，锁文件是 `writer.sqlite`）、
   后台事件列表、授权 JSONL 导出，三者按事件 ID/值核对一致；明确区分“本地已保存”与“服务器已收齐”。
4. 记录：导出文件位置（本地忽略目录）、是否含敏感字段、三处计数与关键 ID/数值。

### WN06 篡改、权限、错平台、缺依赖与旧发行兼容

1. **平台侧**（已由准备门槛在本机真实实例上执行并留档）：存储中的完整包或 sidecar 被篡改后，
   下载与准入都失败关闭；缺少声明依赖或错平台的上传被拒绝；撤销下载权限后下载被拒绝。
2. **客户端侧**：本地复制一份完整包并改动其中一个字节后启动——**程序运行时不做包完整性校验，
   因此不会自动拒绝**；不要把它写成“已拒绝”，这是已知限制，不是通过项。
3. **旧发行兼容**：旧发行（已不是当前发行）仍应能准入、上传并完成；工程检查会真实执行这一项。
4. 记录每个负向场景的实际提示与后台会话数是否保持。

## 三、完成后

1. 按 `WINDOWS_NATIVE_RESULT_TEMPLATE.md` 填好每一项；未做的项目写“未运行/待运行”，
   不要留空、不要把“未运行”写成“通过”。
2. 保留失败现场（截图、程序日志、导出文件）；这些材料留在本地忽略目录，不进 Git。
3. 把填好的结果表交给监督者。只有全部必需项真实通过，Windows 原生实机项才算通过；
   本体验不等于独立 T17，也不替代非开发者独立验收。

## 四、边界说明（不要误解为通过项）

- kit 内的 `integrity.json` 是成员哈希清单（传输完整性），**不是签名**，也不是代码签名；
  SmartScreen/杀毒状态按实际观察记录，不得自动关闭防护或添加信任。
- 哈希校验只证明字节一致，不能证明发布者身份；包未做代码签名。
- 运行时**不做**包完整性校验：本地被篡改的 PCK 不会被程序自动拒绝（已知限制）。
- 本任务固定为两个试次，不存在“再做几次”的可选试次；完成由任务声明，而不是研究者标记后台完成。
- 恢复只支持当前工作流（检查点恢复、六位短码 + 原设备证明、命名恢复）；未声明恢复策略不能
  自动重做或跳过试次。
- 首次准入必须联网；程序关闭后不保证持续上传，重开才恢复队列。
- 清理是逻辑删除，不是取证安全擦除。
